# ADR 0152 — A panic is not an error message

**Status:** Accepted — 2026-10 · §5 made precise by [ADR 0162](0162-the-panic-file-and-the-next-launch.md)

## Context

Leyline reads files it did not write — RAW files from every camera of the
last twenty years, sidecars edited by other tools, a catalog that may have
been copied half-way or restored from an old backup — and its promise is
that the photographer's work is never lost. A panic breaks that promise in
the worst way: Studio vanishes without a word, a batch export of four
hundred photographs stops at the hundred-and-twelfth, and nothing tells the
photographer which file was at fault.

The code says the opposite of what it means in **51 places**. Measured on
2026-10-18 (commit `6833fc6`) with:

```
cargo clippy --workspace --lib --bins -- -A clippy::all \
  -W clippy::unwrap_used -W clippy::expect_used -W clippy::panic \
  -W clippy::unreachable -W clippy::todo -W clippy::unimplemented
```

they fall into three kinds:

* **Infallible by construction**, and saying so in the `expect` message:
  serializing a `Settings` (`leyline-core/src/settings.rs`), the embedded
  Lensfun database (`leyline-lens`), the frozen kernel table
  (`stages/kernel/v3.rs`), `chunks_exact` slices converted to arrays
  (`leyline-color/src/dcp.rs`). They will never fire; the lint cannot know.
* **Reachable from hostile input.** A NaN pixel — which nothing upstream
  rules out: a degenerate matrix in a camera profile is enough — panics in three
  *frozen* stage modules: `stages/tone_curve/v1.rs` (`partial_cmp().unwrap()`),
  `stages/dehaze/v1.rs` (an `expect` on a minimum, and `clamp(1, 0)` on an
  empty image), `stages/hsl/v1.rs` (`unreachable!`). A corrupted catalog
  with a cycle in its collection or keyword tree panics in
  `leyline-catalog/src/collections.rs` and `keywords.rs`; a sidecar whose
  current version is absent panics in `leyline-engine/src/xmp.rs`.
* **Reachable from the environment.** A system clock set before 1970
  (`now_ms` in `leyline-catalog`), a failure to spawn a thread
  (`library.rs`, `watch.rs`, `leyline-tether`).

The rest of `make check` is strict — clippy with no warnings — but nothing
in it stops a fifty-second `expect`.

## Decision

### 1. No panic on a production path

Production code — every crate's library and the two binaries — returns an
error where it can fail, and does not panic. Input that is hostile, corrupted
or merely unexpected (a file, a sidecar, the catalog, the clock, the
operating system) is a case to handle, never a reason to stop.

A panic site stays only when it is **provably infallible**, and then it
carries the proof:

```rust
#[allow(clippy::expect_used, reason = "the database is embedded at build time and parsed by a test")]
```

`reason` is mandatory: an `allow` without one is refused in review. "Cannot
fail" is not a reason; *why* it cannot fail is.

Every panic fixed comes with a regression test that feeds the input which
used to panic.

### 2. The rule is enforced by the compiler, crate by crate

Each production crate root (`crates/*/src/lib.rs`, and `main.rs` for
`leyline-cli` and `leyline-studio`) carries:

```rust
#![deny(
    clippy::unwrap_used,
    clippy::expect_used,
    clippy::panic,
    clippy::unreachable,
    clippy::todo,
    clippy::unimplemented
)]
```

A root `clippy.toml` sets `allow-unwrap-in-tests`, `allow-expect-in-tests`
and `allow-panic-in-tests`: a test that panics is a failing test, which is
what a test is for. Integration tests, benches and `build.rs` are separate
crates and are not covered — a build script that fails is the right
behaviour.

`[workspace.lints]` is **not** used: it would apply to tests and benches as
well, and every crate already inherits it for `missing_docs` and
`clippy::all`.

A crate receives the attribute **once it has no site left**, in the slice
that clears it. The attribute is the proof the slice is done; it is never
added together with a blanket `allow`.

### 3. `unsafe` is forbidden outside two named crates

The same roots carry `#![forbid(unsafe_code)]`, except:

* `leyline-raw` — the LibRaw FFI ([ADR 0004](0004-libraw.md));
* `leyline-cli` — the restoration of `SIGPIPE`'s default disposition, so
  that `leyline … | head` ends quietly.

Neither panic lints nor this one cover code generated by `slint::include_modules!`
in Studio: it is checked by the Slint compiler, not by us.

### 4. Frozen stages keep their output for every input that did not panic

The NaN fixes in `tone_curve/v1`, `dehaze/v1` and `hsl/v1` touch modules
frozen by [ADR 0042](0042-versioned-stage-pipeline.md). They are allowed
because they only change what happens to an input that used to **panic**,
which had no output to preserve. For every other input the output is
identical, bit for bit, and the reference renders do not move.

That excludes `f32::total_cmp`, which orders `-0.0` before `+0.0` where
`partial_cmp` calls them equal, and could therefore reorder a sort on a
sane input. The fix is `partial_cmp(..).unwrap_or(Ordering::…)`, with the
fallback chosen so that NaN lands where it does the least harm.

### 5. A safety net for what the lints cannot see

Lints only see explicit panics. Indexing out of bounds, an integer
overflow in a debug build, a panic inside a dependency are still possible.
So:

* **a panic hook** in Studio and the CLI writes the message and the
  backtrace to stderr and to the log that the problem report joins
  ([ADR 0123](0123-problem-report-bundle.md)); Studio shows it in a window
  built like the startup-failure window ([ADR 0122](0122-startup-failure-window.md))
  rather than disappearing;
* **one photograph's render is isolated** in import and export batches
  (`catch_unwind` around it): a panic becomes a failed item with the file's
  name, and the batch continues;
* the profiles keep `panic = "unwind"` — `abort` would make both of the
  above impossible.

### 6. Hostile input is generated, not only imagined

`proptest` (MIT/Apache-2.0) enters as a dev-dependency, with fixed seeds so
that `make check` stays deterministic. Properties: no stage panics on any
image (NaN, infinities, zero-sized, one pixel); `Settings` and catalog rule
parsers never panic on arbitrary JSON.

### 7. Slices

1. This ADR, the rule in `docs/contributing.md`, `clippy.toml`, and the
   attributes on the crates that are already clean.
2. NaN in the frozen stages (§4), golden unchanged.
3. Catalog cycles, sidecar without its version, the clock, thread spawning,
   `dcp.rs` through `as_chunks`.
4. The infallible sites receive their `allow` with a reason; every
   remaining crate receives its attribute.
5. The safety net (§5).
6. The properties (§6).

## Consequences

* The measuring command above returns nothing once slice 4 is done, and
  `make check` keeps it that way.
* An `expect` in new production code fails `make check`; the author either
  returns the error or writes down why it cannot happen.
* Arithmetic and indexing remain outside the lints. §5 limits their damage
  to one photograph; it does not prevent them.
* A frozen stage module is edited without a new version, which
  [ADR 0042](0042-versioned-stage-pipeline.md) otherwise forbids. The
  exception is narrow — inputs that panicked — and §4 states it so that it
  is not read as a precedent for anything else.

## Alternatives rejected

* **`[workspace.lints]` for the panic lints.** One line instead of
  eighteen, but it would deny `unwrap` in every test, which is noise for
  no safety.
* **`panic = "abort"` in release.** Smaller binaries, and no way to catch a
  panic per photograph or to show it to the photographer.
* **Catching everything at the top (`catch_unwind` around `main`).** Turns a
  crash into a quieter crash: the batch still stops and the catalog
  transaction in flight is still lost. Isolation has to be per photograph.
* **`total_cmp` in the frozen stages.** Simpler, and changes the sort of
  signed zeros on sane input — a silent change to a frozen render.
* **Fixing the 51 sites in one change.** One unreadable diff across thirty
  files; the slices above each leave `make check` green and can be read
  alone.
